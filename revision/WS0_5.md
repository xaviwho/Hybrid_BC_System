would otherwise invalidate v2 measurements, aligns the implementation with the
manuscript's formal model, and creates the **single v2 deployment** that every
later workstream uses. No v2 result is produced here. Every check below was run
on 2026-09-28 against the live stack.

## 4. Consequences for the manuscript and for v1 comparisons

- **v1 and v2 latencies are not directly comparable.** v2 adds the read-back
  query on the acknowledgement path (Alg. 1 l.22 always specified it; v1 did
  not do it) and stores a larger value. v2 reports `readback_ms` as its own
  stage, so its cost is visible. `FABRIC_READBACK=off` allows a like-for-like
  comparison with v1.
- **Gas changes.** `registerData` now checks the allowlist (one extra SLOAD) and
  stores a 66-character c and the canonical m. v1's 273 695 gas per record and
  the Merkle figures are re-measured in WS7 on this contract.
- **Orderer fault tolerance.** The Raft orderer has one consenter, so it
  tolerates no orderer failure. Any crash-fault-tolerance statement about
  ordering needs either a 3- or 5-node Raft cluster (WS2/WS6) or an explicit
  scope-down.
- **Notation.** The manuscript uses τ for both a timestamp (Eq. 20: "version ν
  and timestamp τ") and the sensitivity label (registry tuple (id, h, τ, owner)).
  v2 uses τ = timestamp inside σ; the label is stored in the envelope as
  `sensitivity`.
- **Eq. 21, id = H(x‖t0).** If t0 is server ingress time, a client retry gets a
  new id and is not deduplicated. The implementation uses id = H(x), or an
  explicit `X-Idempotency-Key`. The manuscript should say that t0 is the
  device-assigned timestamp inside x, or drop it from Eq. 21.
