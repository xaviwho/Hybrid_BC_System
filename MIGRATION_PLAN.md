# Migration Plan — running the measurement stack on a new machine

**Goal.** Bring up the full stack on a second machine and produce the three
outstanding measurements — exp1 (latency/throughput), exp3 (gas), exp5
(exactly-once) — then get the results back into the repository.

**Why this is a rebuild, not a copy.** The WSL2 `Ubuntu-22.04` distro on the
current machine has been deleted. It held `/root/fabric-clean` (Fabric runtime
**and its crypto material**), `/root/hybrid-fabric` (chaincode source) and
`/root/orbit-venv` (the Python environment). None of it can be copied because
none of it exists. That is less bad than it sounds: Fabric's crypto material is
regenerated by `network.sh` on every `up`, so it was never worth migrating.

**What actually moves:** the git repository, and nothing else.

---

## 0. Decide the target OS first — it changes everything downstream

| Target | Verdict |
|--------|---------|
| **Native Linux (Ubuntu 22.04)** | **Strongly preferred.** No WSL integration to configure, no drvfs/FAT32 problem, no "Ganache must run inside WSL" caveat, no `/mnt/` path translation. Removes four of the six historical failure modes outright. |
| Windows + WSL2 Ubuntu-22.04 | Workable — it is what the last successful run used — but reintroduces every WSL-specific hazard in §7. |
| macOS | **Not viable as-is.** Fabric's `network.sh` and the pinned `2.5.0`/`1.5.5` images work, but the repo's Fabric binaries are Linux ELF and `fabric_client.py` shells out to the `peer` CLI. Apple Silicon additionally needs `linux/amd64` emulation. Treat as a port, not a migration. |

Everything below is written for **native Linux** with the WSL deltas called out
in §7. If you tell me which the new machine is, I will collapse this to a single
path.

### Host requirements

| Resource | Minimum | Why |
|----------|---------|-----|
| Disk | **25 GB free** | Fabric images ~3 GB, repo clone ~110 MB, node_modules, Go toolchain, CouchDB volumes |
| RAM | 8 GB | 8 Fabric containers + CouchDB + Ganache + two Python services |
| Network | Unmetered | Multi-GB image pulls on first run |
| Docker | 20.10+ | 29.6.1 is what the current machine runs |
| Filesystem for state | **ext4 or equivalent** | The outbox WAL guard refuses to start otherwise (§7.1) |

## 1. Phase A — provision the host

```bash
sudo apt update
sudo apt install -y docker.io docker-compose-plugin git jq curl build-essential

# Go 1.18 — the chaincode declares `go 1.18` in go.mod
sudo apt install -y golang-1.18 || {
  curl -fsSL https://go.dev/dl/go1.18.10.linux-amd64.tar.gz | sudo tar -C /usr/local -xz
  echo 'export PATH=/usr/local/go/bin:$PATH' >> ~/.bashrc && source ~/.bashrc
}

# Node 18+ for ganache/truffle (current machine runs v24; either works)
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash - && sudo apt install -y nodejs

sudo usermod -aG docker $USER && newgrp docker
```

**Gate A — do not continue until all four print:**

```bash
docker version --format '{{.Server.Version}}'   # 20.10+
go version                                       # go1.18.x
jq --version                                     # jq-1.6+
node --version                                   # v18+
```

## 3. Phase C — build the Linux-side runtime

Three directories must be created. **Keep these exact paths** — they are the
defaults compiled into `orchestrator/fabric_client.py`, so using them means no
code changes and `STACK_BRINGUP.md` stays accurate. (Any other location works if
you set `FABRIC_BIN`, `FABRIC_CFG_PATH` and `FABRIC_TEST_NETWORK` instead.)

### C1. Fabric runtime — pristine clone, NOT the repo's copy

```bash
sudo mkdir -p /root/fabric-clean && cd /root
sudo git clone --branch v2.5.0 --depth 1 \
    https://github.com/hyperledger/fabric-samples.git fabric-clean-src
sudo cp -r fabric-clean-src/* /root/fabric-clean/

# binaries + config for 2.5.0 / CA 1.5.5
cd /root/fabric-clean
sudo curl -sSL https://raw.githubusercontent.com/hyperledger/fabric/main/scripts/install-fabric.sh | sudo bash -s -- --fabric-version 2.5.0 --ca-version 1.5.5 binary
```

> **Do not copy `blockchain/setup/hyperledger/fabric-samples` from the repo.**
> `BRINGUP_STATUS.md` records three defects in it that made the network
> un-bringable: a wrong CA volume path, an untagged CA image that pulled
> `:latest`, and `ca_orderer` on port 11054 while `registerEnroll.sh` enrols at
> 9054. It is the reason the network "was never really run" before.

### C2. Chaincode source

```bash
sudo mkdir -p /root/hybrid-fabric/chaincode
sudo cp -r ~/Hybrid_BC_System/blockchain/chaincode/iot-data /root/hybrid-fabric/chaincode/
```

### C3. Python environment

```bash
sudo python3 -m venv /root/orbit-venv
sudo /root/orbit-venv/bin/pip install --upgrade pip
sudo /root/orbit-venv/bin/pip install \
    'web3>=7,<8' 'flask>=3,<4' flask-cors flask-socketio python-socketio \
    python-dotenv requests
```

> **`orchestrator/requirements.txt` is stale — do not use it.** It pins
> `web3==6.0.0` and `Flask==2.3.0`, but the run that actually worked used
> **web3 7.16 and flask 3.1.3** (`BRINGUP_STATUS.md`). `start-system.sh` installs
> the stale pins too — one more reason not to use it (§6). Consider updating
> `requirements.txt` to match reality as a follow-up.

### C4. State directory (ext4 — see §7.1)

```bash
sudo mkdir -p /root/orbit-state
```

**Gate C:**

```bash
ls /root/fabric-clean/bin/peer /root/fabric-clean/config
ls /root/hybrid-fabric/chaincode/iot-data/go/*.go
/root/orbit-venv/bin/python -c "import web3, flask; print(web3.__version__, flask.__version__)"
```

## 4. Phase D — bring the services up

Follow **[STACK_BRINGUP.md](STACK_BRINGUP.md) §1–§5 verbatim.** It has the exact
commands, health checks and failure table, and it is current as of `489b3d41`.
Only two deltas for a fresh machine:

1. **§2 Ganache** — on native Linux, drop the "must run inside WSL" caveat. The
   command is otherwise identical; keep `--networkId 1337` and
   `--wallet.deterministic`.
2. **§3 contract** — the artifact carries 18 stale network entries and a dead
   address. Optionally prune (`networks = {}`) before `truffle migrate --reset`
   so the file stays readable.

**Suggested order, easiest-first**, so a failure is diagnosed against the
smallest possible surface:

| Step | Service | Gate |
|------|---------|------|
| D1 | Ganache | `eth_chainId` → `0x539` |
| D2 | Contract deploy | §3 resolver check prints an address and non-zero code size |
| D3 | **exp3 (gas)** — run it now | 27 real transactions, exit 0 |
| D4 | Fabric | 8 containers + `peer chaincode query` round-trip |
| D5 | Policy engine | `/health` returns `policy_version` |
| D6 | Orchestrator | `/health` shows `ethereum_connected`, `contract_addr`, ext4 `outbox_db`; `/outbox_stats` shows `relay_running: true` |
| D7 | Smoke test | one ingest → **202** → `/anchor_status` → `delivered` with `queue_wait_ms` + `anchor_ms` |

**Running exp3 at D3 is deliberate.** It needs only Ganache and the contract, so
it banks one of the three outstanding measurements before you touch Fabric —
which is the part most likely to fight you.

## 5. Phase E — run the experiments

Per `STACK_BRINGUP.md` §6:

```bash
cd ~/Hybrid_BC_System
export ORCHESTRATOR_URL=http://127.0.0.1:5002
export GANACHE_URL=http://127.0.0.1:8545
V=/root/orbit-venv/bin/python

$V experiments/exp1_latency_real.py      # exit 0 required; exit 2 = gate failure
$V experiments/exp3_gas_real.py
$V experiments/exp5_exactly_once_real.py
$V experiments/exp7_hadc_real.py         # offline, but rerun to record this host's versions
$V experiments/consolidate_results.py
```

### Before consolidating: update the host string

`experiments/consolidate_results.py` hardcodes
`config["host"] = "WSL2 Ubuntu-22.04 + Docker Desktop"`. Change it to the new
machine. This **will change `config_hash`**, and that is correct — a different
environment should hash differently. Record the old hash (`3fa584dfbfc2`) in the
commit message so the two runs remain distinguishable.

### Gate E — what success looks like

```
consolidate_results.py exits 0
  not_measured: []                        ← empty. exp1/exp3/exp5 all admitted
  metrics: run_contract_addr present      ← positive proof of one deployment
  kind_counts: measured > 8
```

**Three ways this legitimately fails, all of them the system working:**

| Signal | Meaning |
|--------|---------|
| exp1 exits **2** | Reconciliation gate failed — observed TPS disagrees with `concurrency / mean_ack_latency`. Writes `exp1_latency_real.FAILED.json`, records no throughput. Investigate; do not rerun until explained. |
| Orchestrator refuses to start | Either a stale contract (no bytecode) or a non-WAL outbox. Both deliberate. See §7.1, §7.2. |
| consolidator exits non-zero | Either an untagged metric, or a **contract address mismatch** across exp1/exp3/exp5 — meaning they did not all use one deployment. Redeploy, restart the orchestrator, rerun all three together. |

**Do not read an empty `not_measured` as success on its own.** Confirm
`run_contract_addr` is present. If it is missing, the cross-check did not run.

### Also record, for F-A

exp7's result is **not reproducible across zlib builds** — the current machine
gives 6.25% savings and `heterogeneous_selection: true`, the original WSL host
gave 4.2% and `false`. Capture on the new machine:

```bash
/root/orbit-venv/bin/python -c "import sys, zlib, platform; \
print(sys.version, platform.platform(), zlib.ZLIB_RUNTIME_VERSION)"
```

A third data point will tell you whether the variance is zlib-version-driven or
something else. See `experiments/results/exp7/exp7_ENVIRONMENT_COMPARISON.json`.

## 6. Do not use the convenience scripts

`start-system.sh` and `start-hybrid-network.sh` will produce a stack that looks
up and is not:

- **`deployCC` appears zero times in `start-system.sh`** — Fabric comes up with a
  channel but **no chaincode**, so every ingest returns 502
- points at the repo's corrupted `fabric-samples`
- `network.sh up -s couchdb` with no `-ca` and no image tags
- Ganache via docker with no chainId/networkId/deterministic pin
- starts the orchestrator with **zero env vars** — wrong policy port, wrong
  Fabric paths, and `OUTBOX_DB` on the repo filesystem
- installs the stale `web3==6.0.0` pins
- writes `.running-services` claiming everything is up

## 7. Risk register

### 7.1 The outbox WAL guard (**will bite you if state is not on ext4**)

`OUTBOX_DB` defaults to the orchestrator package directory. On a Linux-native
machine with the repo on ext4 that is fine. On WSL with the repo on a Windows
drive it lands on drvfs, where SQLite silently declines WAL — and
`Outbox.__init__` now raises rather than run without it:

```
RuntimeError: outbox at '...' is in journal_mode='delete', not 'wal'.
```

**Always set `OUTBOX_DB=/root/orbit-state/outbox.db` explicitly.** Verify:

```bash
sqlite3 /root/orbit-state/outbox.db 'PRAGMA journal_mode;'   # must print: wal
```

### 7.2 Contract address

Ganache starts with fresh state, so the contract must be redeployed and the old
address (`0xe78A0F7E598Cc8b0Bb87894B0F60dD2a88d6a8Ab`) is dead. The orchestrator
now **refuses to start** if the resolved address holds no bytecode. Always:
redeploy → verify → *then* start the orchestrator. Restart the orchestrator after
any redeploy — it resolves once at import.

### 7.3 Fabric CA enrolment

The single most likely failure. Mitigations, in order: use `/root/fabric-clean`
(pristine) not the repo copy; pass `-i 2.5.0 -cai 1.5.5` on **both** `up` and
`createChannel`; if enrolment hangs, `./network.sh down` and start clean rather
than retrying in place.

### 7.4 Port conflicts

5001 was occupied by an unrelated service on the current machine, which is why
the policy engine runs on **5011**. Check the new host before assuming:

```bash
ss -lptn 'sport = :5001 or sport = :5002 or sport = :8545 or sport = :7051'
```

### 7.5 Results divergence — pick one measurement host

`experiments/results/` is now git-tracked. If both machines run experiments, they
will conflict on `RESULTS.json`.

**Rule: the new machine is the measurement host.** This machine must not rerun
any experiment or regenerate `RESULTS.json` until the new machine's results are
merged back.

### 7.6 Timing measurements and machine load

exp1 and exp4 are latency experiments. Run them on an otherwise idle machine —
no builds, no other containers. Different hardware will produce different
absolute latencies, which is expected and fine, but they must be internally
consistent within one run.

## 8. Phase F — getting results back

The results tree is tracked, so results return the same way the code arrived:

```bash
cd ~/Hybrid_BC_System
git add experiments/results/ experiments/consolidate_results.py
git commit -m "Measurements from <new host>: exp1, exp3, exp5 on live stack

Host: <cpu/os>. Python <ver>, zlib <ver>, web3 <ver>, Fabric 2.5.0/CA 1.5.5.
config_hash <new> (was 3fa584dfbfc2 on the previous host).
not_measured empty; run_contract_addr <0x...> confirms a single deployment."
git push
```

Also commit `experiments/results/exp1/exp1_requests.jsonl` — the per-request rows
are what make p95 of ack latency derivable, and they are the only artifact that
survives a gate failure.
